为什么换了小模型还是慢
这是 ComfyUI 的固定行为，跟显存够不够无关：

每个不同的 LoRA 权重都会 load_lora_for_models → model.clone()（
comfy/sd.py:107
），clone 和原模型共享同一个 BaseModel，但对象不同
load_models_gpu 在装载新 clone 时，会先把所有 is_clone 的旧模型 detach 到 CPU：

is_clone 判断的是 self.model is other.model：

，所以前一个权重变体必然被认成同一个模型的旧 clone

也就是说：即使 32GB 全空着，ComfyUI 也会先卸旧 clone、再装新 clone。CLIP 同理（CR Apply LoRA Stack 同时克隆 CLIP），所以 T5 每张也重载。

--disable-dynamic-vram 开启与关闭的区别
这个参数用来强制关掉动态 VRAM（comfy-aimdo），回退到旧的“按估算加载”模式。在 NVIDIA 显卡上，默认是开启的（
cli_args.py:326
）；此外，--highvram、--gpu-only、--novram、--cpu 也会间接关掉它，而 --lowvram 在动态模式下完全无效。
一、两条加载路径的核心差异
项目	动态 VRAM（不加该 flag）	--disable-dynamic-vram（旧模式）
加载器类	ModelPatcherDynamic（
main.py:268
）	ModelPatcher
加载时做什么	只分配虚拟地址空间（VBAR）并固定宿主缓冲，权重按模块按需搬运	按估算把整个模型搬到显存
日志特征	... prepared for dynamic VRAM loading. X MB Staged. N patches attached.（
model_patcher.py:2034
）	loaded completely; ... MB loaded, full load: True（
model_patcher.py:1099
）
显存不够时	由 VBAR 分页按需换入换出，模型可以比显存大	先整模 unload 别的模型；仍不够就走 lowvram 部分加载
腾显存策略	在 free_memory(for_dynamic=True) 中不会为了动态模型去卸载其他动态模型（
model_management.py:893
）	会把其他模型整体卸载/搬到 CPU
附带能力	NVML 显存压力监测、异步 offload（N 卡默认 2 流）、--fast-disk 磁盘直载、--vram-headroom、Linear 懒初始化（跳过 torch.empty，避免 Windows 重复 commit）、prefetch/comfy compiler 依赖 aimdo	以上全部不可用
补充两点：

GGUF/量化格式：官方在
main.py:602
 明确警告“用 GGUF 建议保留动态 VRAM，并尽量换原生 fp8/int8/w4a8 格式”，且该 flag 计划被移除。
显存曲线：动态模式下权重的换入是分页流式的；旧模式是整体加载、整体卸载，所以你截图里那种满上─掉下来的锯齿，是旧模式的典型形态。
二、与你的 LoRA 权重对比直接相关
load_models_gpu 里“同底模的旧 clone 先 detach”这段逻辑两种模式都有（
model_management.py:981
），所以：
换一个 LoRA 权重 = 新 model.clone() = 旧 clone 被驱逐，这个机制不会因为开关而消失；
差别在驱逐之后要搬多少东西：旧模式每次按估算把 11.35 GB UNET 整体重走一遍加载（你日志里每张都有 loaded completely ... full load: True），这就是 ~6.6s 的来源；动态模式的权重页挂在共享的 base model 的 VBAR 上，detach 本身不搬权重，没被 LoRA 改到的模块可以复用，只有被 patch 的层需要重算/重搬。
实际收益取决于 LoRA 覆盖范围：Flux LoRA 通常打满所有线性层，那收益会缩小到“流式加载一次”的量级；只改部分层的 LoRA 提速会更明显。这点建议实测确认，不要只看机制推断。
另外，动态模式下前端队列、/free、节点逻辑都一样，前端仍然不是瓶颈（上次测过 3 个权重 2 秒内就全部提交了）。

三、给你的实际建议
当前命令行带着 --disable-dynamic-vram，所以你看到的是旧模式的整模重载。建议去掉该 flag，用同一组 3 权重对比跑一遍，比较每张耗时和任务管理器曲线；启动日志会从 Dynamic vram disabled with argument 变成 DynamicVRAM support detected and enabled，加载日志会从 loaded completely 变成 prepared for dynamic VRAM loading。
注意代价：动态模式会 pin 宿主内存（Windows 上限约系统 RAM 的 40%，
model_management.py:1640
）。11.9 GB UNET + 3 GB T5 的场景下如果内存吃紧，可加 --disable-pinned-memory，或者用 --fast-disk 走 NVMe。
如果动态模式下出现显存抖动/驱动压力问题，用 --vram-headroom 1~2 或 --reserve-vram 调，而不是退回去；--lowvram 在动态模式无效，别同时加。
最根本的提速仍是让整组权重在同一个 prompt 内循环（同一个 ModelPatcher、只换 patch），这样连 clone 驱逐都不会发生；调 flag 只是把“每次重载 11 GB”降级成“每次流式补 LoRA 涉及的层”。
